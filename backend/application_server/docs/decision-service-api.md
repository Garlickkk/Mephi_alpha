# Сервис принятия решений: ожидаемое API

Этот документ описывает API, который сервис заявок (`application_server`) ожидает от сервиса принятия решений.
Сам сервис принятия решений в этом репозитории не реализован. Здесь зафиксированы контракты, на которые опирается
сервис заявок, и правила обмена.

## 1. Роль сервиса

- Получает заявку с данными клиента и условиями кредита.
- Проверяет и оценивает заявку: скоринг, проверки внешних источников (бюро кредитных историй, ЕГРЮЛ/ЕГРИП,
  «Прозрачный бизнес»), внутренние правила банка.
- Возвращает одно из решений: одобрено, отказано, компромиссные условия или «на рассмотрении».
- Для асинхронного решения вызывает callback сервиса заявок.

Сервис заявок не передаёт JWT клиента и не знает внутренних процессов решения. Он передаёт только
данные, нужные для решения.

## 2. Общие правила

| Параметр | Значение |
|----------|----------|
| Базовый путь | `/api/v1` |
| Формат | JSON, `Content-Type: application/json`, кодировка UTF-8 |
| Даты | ISO-8601: `yyyy-MM-dd` для дат, `yyyy-MM-ddTHH:mm:ss.SSSZ` для времени (UTC) |
| Деньги | рубли, число с двумя знаками после запятой |
| Ставка | % годовых, число с двумя знаками после запятой |
| Аутентификация | межсервисная: заголовок `X-Service-Token` (тот же механизм, что у callback'а) или mTLS в продакшене |
| Таймаут на стороне сервиса заявок | 5 секунд (`DECISION_TIMEOUT`) |

Сервис заявок ожидает ответ на синхронный вызов в пределах таймаута. Если решение требует времени (ручная проверка),
отвечайте сразу статусом `PENDING` и отправьте результат callback'ом.

## 3. Эндпоинты

### 3.1. POST /api/v1/decisions: отправить заявку на рассмотрение

Вызывается сервисом заявок сразу после сохранения заявки.

**Заголовки**

| Заголовок | Обязательный | Описание |
|-----------|--------------|----------|
| `Content-Type` | да | `application/json` |
| `Idempotency-Key` | да | id заявки в сервисе заявок (строка). Повторный запрос с тем же ключом не создаёт новое решение, а возвращает уже существующее |
| `X-Service-Token` | да | межсервисный токен |

**Тело запроса**

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `applicationId` | integer (int64) | да | id заявки в сервисе заявок |
| `client` | object | да | данные клиента (см. ниже) |
| `client.inn` | string (10 или 12 цифр) | да | ИНН |
| `client.organizationType` | enum `OOO`, `IP`, `AO` | да | тип организации |
| `client.okvedMain` | string | да | основной ОКВЭД, например `62.01` |
| `client.registrationDate` | string (date) | да | дата регистрации |
| `loan` | object | да | запрошенные условия |
| `loan.rate` | number | да | ставка, % годовых |
| `loan.amount` | number | да | сумма кредита, руб. |
| `loan.durationYears` | integer | да | срок, лет |
| `loan.purpose` | string | да | цель кредита |
| `loan.collateral` | boolean | да | есть ли залог |
| `product` | object или null | нет | снимок продукта из каталога, если клиент выбрал готовый продукт; `null` при подаче по калькулятору |
| `product.id` | integer | да (если `product` передан) | id продукта |
| `product.title` | string | да | название |
| `product.interest` | number | да | базовая ставка продукта |
| `product.discountInterest` | number | да | ставка со скидкой |
| `product.discountConditions` | string или null | нет | условия скидки |
| `product.minSum`, `product.maxSum` | integer | да | лимиты суммы |
| `product.minDurationYear`, `product.maxDurationYear` | integer | да | лимиты срока |
| `product.repaymentTypes` | array of enum | да | `EQUAL_PRINCIPAL_PARTS`, `EQUAL_TOTAL_PARTS` |
| `product.mainDifference` | string | да | главное отличие продукта |
| `requestedAt` | string (date-time) | да | момент отправки заявки сервисом заявок |

**Пример запроса (готовый продукт)**

```json
{
  "applicationId": 17,
  "client": {
    "inn": "7701234567",
    "organizationType": "OOO",
    "okvedMain": "62.01",
    "registrationDate": "2020-05-14"
  },
  "loan": {
    "rate": 12.50,
    "amount": 800000.00,
    "durationYears": 3,
    "purpose": "Пополнение оборотных средств",
    "collateral": true
  },
  "product": {
    "id": 1,
    "title": "Потребительский кредит",
    "interest": 12.50,
    "discountInterest": 10.50,
    "discountConditions": "при оформлении страховки",
    "minSum": 50000,
    "maxSum": 3000000,
    "minDurationYear": 1,
    "maxDurationYear": 5,
    "repaymentTypes": ["EQUAL_TOTAL_PARTS", "EQUAL_PRINCIPAL_PARTS"],
    "mainDifference": "Без залога и поручителей"
  },
  "requestedAt": "2026-10-25T10:12:31.114Z"
}
```

**Пример запроса (калькулятор, продукта нет)**: поле `product` равно `null`, остальное так же.

**Ответы**

| Код | Когда | Тело |
|-----|-------|------|
| `200 OK` | решение принято сразу (`APPROVED`, `REJECTED`, `COUNTER_OFFER`) | `DecisionResponse` |
| `202 Accepted` | решение требует ручной проверки (`PENDING`), результат придёт callback'ом | `DecisionResponse` с `outcome = PENDING` |
| `400 Bad Request` | некорректные данные (нет обязательного поля, неверный enum) | `ErrorResponse` |
| `401`, `403` | нет или неверный `X-Service-Token` | `ErrorResponse` |
| `409 Conflict` | `Idempotency-Key` уже использован с другим содержимым | `ErrorResponse` |
| `503 Service Unavailable` | сервис временно недоступен | `ErrorResponse` |

**Пример ответа `200` (одобрено)**

```json
{
  "decisionId": "dec_7f3a9c",
  "outcome": "APPROVED",
  "comment": "Заявка одобрена на запрошенных условиях",
  "counterOffer": null
}
```

**Пример ответа `200` (компромиссные условия)**

```json
{
  "decisionId": "dec_7f3a9d",
  "outcome": "COUNTER_OFFER",
  "comment": "Одобрена сумма 500 000 руб. при сроке 2 года",
  "counterOffer": {
    "rate": 13.90,
    "amount": 500000.00,
    "durationYears": 2
  }
}
```

**Пример ответа `202` (ручная проверка)**

```json
{
  "decisionId": "dec_7f3a9e",
  "outcome": "PENDING",
  "comment": "Заявка передана сотруднику на проверку",
  "counterOffer": null
}
```

### 3.2. GET /api/v1/decisions/{decisionId}: получить решение

Опционально. Нужен для мониторинга и ручной сверки, сервис заявок его не вызывает.

Ответ `200 OK`: `DecisionResponse`. Ответ `404`, если решения с таким id нет.

## 4. Объекты ответа

### DecisionResponse

| Поле | Тип | Описание |
|------|-----|----------|
| `decisionId` | string | id решения в сервисе принятия решений, сохраняется в заявке |
| `outcome` | enum | `APPROVED`, `REJECTED`, `COUNTER_OFFER`, `PENDING` |
| `comment` | string или null | пояснение для клиента, показывается в личном кабинете |
| `counterOffer` | object или null | обязателен при `COUNTER_OFFER`, иначе `null` |

### CounterOffer

| Поле | Тип | Описание |
|------|-----|----------|
| `rate` | number или null | предлагаемая ставка; `null`, если ставка не меняется |
| `amount` | number или null | предлагаемая сумма; `null`, если сумма не меняется |
| `durationYears` | integer или null | предлагаемый срок; `null`, если срок не меняется |

Хотя бы одно из трёх полей должно отличаться от запрошенных условий. Иначе это не компромисс, а одобрение.
Поля, равные `null`, сервис заявок показывает клиенту как «без изменений».

### ErrorResponse

```json
{ "message": "Текст ошибки", "dateTime": "2026-10-25T10:12:31" }
```

## 5. Callback: асинхронное решение

Если сервис принятия решений вернул `PENDING`, итоговое решение он отправляет сервису заявок.

**Эндпоинт сервиса заявок**

```
POST {APPLICATION_SERVICE_URL}/api/v0/internal/applications/{applicationId}/decision
X-Service-Token: <INTERNAL_SERVICE_TOKEN>
Content-Type: application/json
```

**Тело**

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `decisionId` | string | да | id решения, полученный при `PENDING` |
| `outcome` | enum | да | `APPROVED`, `REJECTED`, `COUNTER_OFFER` (`PENDING` не отправляется) |
| `comment` | string | нет | пояснение для клиента |
| `counterOffer` | object | да, если `COUNTER_OFFER` | см. `CounterOffer` |

**Пример**

```json
{
  "decisionId": "dec_7f3a9e",
  "outcome": "APPROVED",
  "comment": "Проверка пройдена, заявка одобрена",
  "counterOffer": null
}
```

**Ответы сервиса заявок**

| Код | Когда |
|-----|-------|
| `200 OK` | решение применено. Тело: `ApplicationResponse` с новым статусом. Повтор того же callback'а с тем же `decisionId` тоже даёт `200` (идемпотентность) |
| `400` | `COUNTER_OFFER` без `counterOffer` или некорректное тело |
| `403` | неверный `X-Service-Token` |
| `404` | заявка с таким id не найдена |
| `409` | заявка уже имеет итоговый статус, полученный из другого решения |

**Повторы.** Сервис принятия решений повторяет callback при сетевой ошибке и при кодах `5xx`, с экспоненциальной
задержкой (например, 1 с, 2 с, 4 с, до 5 попыток). Коды `2xx` и `409` считаются завершёнными попытками.

## 6. Соответствие статусов

| `outcome` сервиса решений | Статус заявки в сервисе заявок | Что видит клиент |
|---------------------------|--------------------------------|------------------|
| `APPROVED` | `ACCEPTED` | заявка принята |
| `REJECTED` | `REJECTED` | заявка отклонена, `comment` с причиной |
| `COUNTER_OFFER` | `COUNTER_OFFER` | предложены условия, нужно принять или отклонить |
| `PENDING` | `UNDER_CONSIDERATION` | заявка на рассмотрении |

После `COUNTER_OFFER` ответ клиента обрабатывает сервис заявок (`POST /applications/{id}/counter-offer`).
Сервис принятия решений о нём не узнаёт, пока не будет реализована обратная связь. Если она понадобится,
её нужно добавить отдельным эндпоинтом.

## 7. Что сервис заявок уже проверяет сам

Чтобы не дублировать работу, сервис заявок до отправки проверяет:

- сумма и срок в пределах лимитов готового продукта (если `product` передан);
- тип организации в калькуляторе совпадает с типом из токена;
- обязательность полей калькулятора и формат данных.

Сервис принятия решений может проверять лимиты повторно и должен возвращать `400`, если они нарушены.

## 8. Что не входит в контракт

- Подписание документов и выдача денег. По ограничениям задачи они моделируются и не нужны в сервисе решений.
- Хранение заявок и статусов. Это ответственность сервиса заявок, сервис решений хранит только историю своих решений.
- Пользовательский интерфейс и уведомления.

## 9. Для разработки без реального сервиса

На время разработки можно поднять заглушку, которая на `POST /api/v1/decisions` всегда возвращает
`{"decisionId":"stub-1","outcome":"APPROVED","comment":"stub","counterOffer":null}` со статусом `200`.
Такая заглушка покрывает основной сценарий. Для проверки ветки компромисса и асинхронного решения можно сделать
вторую заглушку, которая возвращает `COUNTER_OFFER` или `PENDING` и затем вызывает callback.

## 10. Реализованный scoring-service в этом репозитории

В `../decision_service` добавлен FastAPI-сервис на порту `8090`, совместимый с описанным выше `POST /api/v1/decisions`.
Он адаптирует существующий Java-контракт к скоринговой карте из 12 факторов. Пока реальные РКО/БКИ/оценка залога отсутствуют,
они воспроизводятся детерминированными локальными моками; точка замены находится в `deterministic_external_mocks()`.
Дополнительно сервис возвращает `score`, `riskGrade`, `interestRate`, `monthlyPayment`, `dtiRatio`, `profitabilityMargin`,
а `application_server` сохраняет и возвращает эти поля в `ApplicationResponse`. Метрики, не имеющие смысла для исхода
(ставка и платёж при отказе), равны `null`.

Реализованы также: идемпотентность по `Idempotency-Key` (409 при другом содержимом), `PENDING` с ответом `202` для
ручной проверки (рейтинг D или сумма свыше 30 млн), `GET /api/v1/decisions/{decisionId}`, очередь
`GET /api/v1/decisions?status=PENDING` и `POST /api/v1/decisions/{decisionId}/resolve`, после которого сервис отправляет
callback с повторами (раздел 5). Подробности и тестовые клиенты — в `../decision_service/README.md`.
