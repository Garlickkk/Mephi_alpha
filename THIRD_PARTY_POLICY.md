# Политика учёта сторонних компонентов

Требование PDF (стр. 7) — файл `THIRD_PARTY_NOTICES`; отдельный `THIRD_PARTY_POLICY.md` регламентом не предписан. Этот документ задаёт порядок сопровождения перечня.

1. При добавлении библиотеки, изображения, шрифта, модели, датасета или сервиса обновлять [THIRD_PARTY_NOTICES](THIRD_PARTY_NOTICES): источник, версия/commit, лицензия или условия, назначение, изменённые файлы, необходимость при запуске.
2. Фиксировать версии ключевых зависимостей в POM, requirements или конфигурации образов. Сохранять лицензионные уведомления при копировании ресурсов. Лицензия основной программы не заменяет лицензии пакетов Docker-образа.
3. Проверяемая версия работает без платных API, корпоративных систем и покупных данных. Использовать синтетические данные; описывать моки и упрощения.
4. Если в runtime появится LLM, использовать только модель с открытыми весами, указать ревизию, источник весов и условия. Сейчас LLM и обучаемых ML-моделей нет.
5. Инструменты разработки учитывать отдельно. Сгенерированный ресурс включать в репозиторий, чтобы запуск не требовал повторной генерации.
6. Перед сдачей сверять перечень с POM, requirements, Dockerfile и frontend/assets. Транзитивные зависимости проверять отдельно: Java — `sh ./mvnw dependency:tree`, Python — `python -m pip freeze` в окружении сборки.

Перечень описывает известные компоненты и ограничения проверки, а не полный SBOM системных пакетов. Неподтверждённое происхождение или уведомление отмечается явно. Политика не назначает лицензию собственному коду команды и не заменяет лицензии сторонних авторов.
