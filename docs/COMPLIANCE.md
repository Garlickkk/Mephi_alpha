## Что фактически проверено

- `docker compose config --quiet` — успешно.
- Сборка всех пяти образов — успешно: frontend, user_server, product_server, application_server, decision_service.
- Запуск отдельного Compose-проекта `mephi-regulation-check` с портами 18085/18090 и новыми томами: восемь сервисов healthy (пять приложений и три БД).
- API E2E по данным `demo/clients.json`: регистрация, собственный профиль, каталог, заявка и история для пяти клиентов; ожидаемые ACCEPTED, два COUNTER_OFFER, REJECTED, UNDER_CONSIDERATION подтверждены.
- Условия предложений подтверждены: 4 года для клиента 2; 1 510 000 руб. на 5 лет для клиента 3. Принятие и отклонение работают.
- Ручное решение клиента 5: callback `DELIVERED`, итоговая заявка `ACCEPTED`.
- Негативные проверки: без токена 401, чужая заявка 404, сумма вне продукта 400, повторный ответ на counter-offer 409.
- Frontend: 9 тестов прошли на Node.js 22.14.0.
- `ProfileAccessTests`: 3 теста прошли, Maven BUILD SUCCESS.
- JSON и внутренние `$ref` OpenAPI проверены; маршруты и поля основных моделей Decision OpenAPI сверены с `app.openapi()` из контейнера.

Полный браузерный сценарий, нагрузочные проверки, восстановление после потери БД и все строки TEST_SCENARIOS не выполнялись. Postman-коллекция проверена как JSON, не запускалась отдельным Runner. Сквозная проверка выполнялась HTTP-запросами к тому же proxy.

## Известные технические ограничения MVP

Это отдельные риски для критериев enterprise-разработки, а не дополнительные выдуманные требования к комплекту сдачи:

- У decision_service очередь/идемпотентность в памяти, нет общего состояния реплик; у application_server нет повторной отправки при недоступном скоринге.
- Нет версионируемых миграций, production TLS, персональной роли сотрудника и рабочего места андеррайтера. API ручного решения защищён общим токеном.
- Исходные Java properties содержат демонстрационные секреты. Compose переопределяет их и задаёт разумные сроки токенов; для публичной среды нужны собственные значения.
- user_server не имеет ADMIN в enum, method security и общего обработчика ошибок. Некорректная регистрация может давать 500. Это отражено в API-документации, а не представлено как исправленное поведение.
- Каталог не содержит eligibility-полей возраста/типа/залога; UI не может фильтровать по ним. Скидка не применяется автоматически; график дифференцированного платежа не рассчитывается frontend.
- Подписание и выдача денег не входят в реализованный MVP. Балльная модель учебная и не является банковской моделью риска.

Проверочный стенд после прогона остановлен; его отдельные тома сохранены. Основной стенд и существующие данные пользователя не останавливались и не удалялись.
